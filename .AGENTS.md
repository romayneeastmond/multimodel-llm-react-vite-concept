# Agent Guidelines for Multi-Model Orchestrator

This document provides guidelines for AI agents working on this codebase.

## Code Comments Policy

**DO NOT add obvious or redundant comments to the code.**

### ❌ Bad Examples (DO NOT DO THIS)
```typescript
// Initialize with empty string if no value is set
React.useEffect(() => {
    if (values[name] === undefined) {
        setFieldValue(name, '');
    }
}, [name, values, setFieldValue]);

// Set the user message
const userMessage: Message = { ... };

// Loop through items
items.forEach(item => { ... });
```

### ✅ Good Examples (Only add comments when necessary)
```typescript
// ONLY add comments for:

// 1. Complex business logic that isn't immediately obvious
// Note: We pass empty history array to make A2UI submissions independent of conversation context
const text = await generateModelResponse(firstModel, toolCallMessage, [], currentTools, systemInstruction, []);

// 2. Workarounds or non-obvious solutions
// Workaround: sessionStorage can interfere with multi-select state, so we clear it on submit
sessionStorage.removeItem(`a2ui_values_${formId}`);

// 3. Important warnings or gotchas
// IMPORTANT: This must run before the form is submitted or data will be lost
validateFormData();
```

## General Coding Standards

### Code Quality
- Write self-documenting code with clear variable and function names
- The code itself should explain what it does
- Comments should only explain **why**, not **what**

### TypeScript
- Use proper TypeScript types, avoid `any` when possible
- Leverage type inference where appropriate
- Use interfaces for complex object shapes

### React
- Use functional components with hooks
- Keep components focused and single-purpose
- Use `useCallback` and `useMemo` appropriately for performance

### Formatting
- Follow existing code style in the project
- Use consistent indentation (tabs in this project)
- Keep lines reasonably short (under 120 characters when practical)

### State Management
- Use React hooks for local state
- Keep state as close to where it's used as possible
- Avoid unnecessary re-renders

## File Organization

- Components go in `src/components/`
- Services go in `src/services/`
- Types go in `src/types/`
- Utilities go in `src/utils/`

## Testing Changes

When making changes:
1. Ensure the dev server is running (`npm run dev`)
2. Test the functionality in the browser
3. Check for console errors
4. Verify TypeScript compilation succeeds

## Summary

**The golden rule: If the code is clear, don't add comments. If you must add a comment, explain WHY, not WHAT.**
